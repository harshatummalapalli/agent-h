6. The actual sourcing engine design — one engine, two trigger modes
This is the most important conceptual outcome of the session and should anchor the eventual orchestrator build (Section 8, build order item 6 from the 2026-07-20 handoff). Confirmed explicitly with Harsha: it's one pipeline, not two products.

Shared engine, regardless of trigger:

1. Query compiler — deal's stored criteria (`required_skills`, `must_have_keywords`, `excluded_companies`, `exclusion_keywords`, `past_titles`, `past_companies`, company size/industry) compiled into the canonical IR, narrowest-first.
2. Vendor fan-out — parallel calls to whichever data sources are live (today: Coresignal, free-portals/GitHub, Exa; Crustdata pending evaluation).
3. Relevance filter — `isCandidateRelevantToDeal` (or its Coresignal-side equivalent once built) gates every candidate before it's savable, regardless of which trigger mode is running.
4. Evidence-based ranking — `candidate_scores`/`candidate_fit_assessments` with `quote_verifications`, never a black-box similarity score. Explicit anti-pattern named and rejected: LinkedIn's own "more profiles for you" panel (seen in the Dover video, Section 7) — a recommendation with zero stated reason. Every candidate we surface must carry a concrete, checkable reason it's there.
5. `sourcing_runs` — the audit trail for every run of the engine, either trigger mode.

Two trigger modes on top of the same engine:

* On-demand (chat-triggered): a recruiter asks right now via the sidebar. Runs once. If the narrow query comes up thin, relaxation stays a conversation — the system says so and the recruiter decides whether to loosen something (matches the existing `relax_criterion` command-bar action), rather than the system silently deciding for them.
* Continuous ("toughest role," relentless): a recruiter flags a role (new field needed: `deals.continuous_sourcing_enabled` + a frequency setting) and the engine runs on a schedule (nightly or as configured) without anyone watching. This is where the relaxation ladder needs to be autonomous, and needs its own guardrails:
  - Allowlisted relaxable fields only — company size, years-of-experience, must-have-keyword downgrades. `required_skills` and `excluded_companies` should never auto-relax (they exist for real reasons — a required skill is required, an excluded company is very often a client or a do-not-poach).
  - Every relaxation event logged in `sourcing_runs` (query_params already captures the IR sent, run over run) and surfaced as a one-line disclosure in the Inbox ("widened company size after 3 quiet nights") — never silent drift.
  - A hard cap on relaxation steps before the system stops loosening and asks the recruiter directly, rather than drifting indefinitely.
  - Relaxation attempts count against a per-role nightly credit budget, decided up front — continuous sourcing across many "toughest roles" compounds cost in a way one-off manual searches don't; this needs to be designed in from the start, not discovered later on a bill.
  - Results still land in the existing Triage Inbox — no new delivery surface needed, just a new entry type feeding the same ranked queue.
7. Outreach — findings, not yet built
Investigated what happens once a candidate is sourced and contact info is needed.

* Confirmed via schema, not assumption: `candidates` already has `email_jsonb`, `phone_jsonb`, `contact_enrichment_raw`, `contact_enrichment_status`, `contact_enrichment_source`, `contact_enrichment_updated_at` — a deliberately separate step from sourcing. Coresignal/Crustdata's profile data does not reliably include usable email/phone; there's already a dedicated `enrich-candidate-contact` edge function plus test functions for Hunter, Apollo, and PDL (specialist contact-finding/verification vendors) in the project for exactly this reason.
* Reviewed a Dover product demo video (their Chrome sourcing extension) at Harsha's request, to answer "how do they do outreach without LinkedIn InMail." Confirmed by watching the actual demo frame: they don't use LinkedIn's messaging system at all. The extension reads a LinkedIn profile the recruiter is already viewing (a content script parsing the rendered DOM of an authenticated session, not a bulk scrape), guesses the person's work email from their current employer's domain (firstname.lastname@company convention), and sends a normal email through the recruiter's own connected mail account — landing in the candidate's regular inbox, fully bypassing LinkedIn. Also noted: a "job + campaign" picker (saved outreach persona/template) and an explicit "add without sending outreach" option (decoupling pipeline-add from the send decision) — both worth adopting patterns.
* Genuine gap identified, not yet built: `deal_candidates` has no stage/status/outreach tracking at all (only `id`, `tenant_id`, `org_type`, `deal_id`, `candidate_id`, `sourced_via`, `match_score`). There's real downstream infrastructure already (Postmark inbound handling, reply-threading, Cal.com booking links, interview reminders, offer-sending) but nothing bridges "just sourced" to "actively being contacted." This is the next concrete piece once sourcing itself is solid: an outreach stage on `deal_candidates` (contacted_at, response_status, reply thread) plus a send-first-outreach function that drafts messages from the real fit-assessment evidence already stored in `candidate_scores`/`candidate_fit_assessments` — grounded in specifics, not the generic template Dover's own demo shows.
* Browser-extension approach explicitly ruled out by Harsha for this platform, and independently flagged as high-risk regardless: a prior session already evaluated and declined the same category of approach (a code comment in `dataProvider.ts` references "the declined BrightData/direct-LinkedIn-automation path"). Running Dover-style logic server-side with a recruiter's own stored LinkedIn credentials to keep "sourcing while their laptop is closed" was raised and rejected this session too — the ban risk lands on the individual recruiter's personal LinkedIn account (not our infrastructure), and storing/reusing real login credentials for automated access is a credential-security line not worth crossing. Do not revisit this path. The actual mechanism for "sources while you sleep" is the continuous-mode engine in Section 6, which never touches a recruiter's own LinkedIn session.
