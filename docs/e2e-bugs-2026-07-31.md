# E2E Bug Report — 2026-07-31

## Bug #1 — Duplicate candidates (HIGHEST)

**Files:** `supabase/functions/_shared/crustdataClient.ts` (`normalizeCrustdataProfile` id fallback), `supabase/functions/calibration-session/index.ts` (merge/dedup).

**Root cause:**
- `normalizeCrustdataProfile` falls back to `id: ""` (empty string), which acts as a dedup key and collapses all empty-id profiles into one slot.
- Dedup key in calibration-session is `c.linkedin_url || c.id` — when linkedin_url uses different formats (with/without `https://`, `www.`, trailing slash) they generate different keys for the same person.
- No content-fingerprint second pass before persist.

**Fix:**
1. Never default `id` to `""`. Fallback chain: `crustdata_person_id` → normalized linkedin_url → content fingerprint (`name+company+location`). Empty string must never be a dedup key.
2. Add `_shared/normalizeLinkedinUrl.ts` (strip protocol, www, trailing slash, query, lowercase). Use as dedup key everywhere linkedin is compared — inside `searchCrustdataForRoleBrief` before return (dedupe firstFiltered/retryFiltered) and calibration-session merge (`key = normalizeLinkedinUrl(url) || id`).
3. Second-pass content-fingerprint dedupe on `merged` before persist to `cache.payload` (normalized name + company).
4. Unit tests: two profiles same person different linkedin URL formats → one entry; empty `crustdata_person_id` doesn't collide distinct people.

## Bug #2/#3/#4 — Two parsers, one truth (Prefer-tab / SearchIntentEditor / display)

**Files:** `src/components/atomic-crm/roles/SearchIntentEditor.tsx`, `SearchIntentDisplay.tsx`, `RoleWorkspacePage.tsx`, `supabase/functions/resolve-search-intent/`, `supabase/functions/parse-job-description/`.

**Root cause:**
- Prefer-tab / SearchIntentEditor / display reads Stage 2 `parsedBriefToConditions` mapping instead of Stage 3 `VersionedSearchIntent`.
- `unenforceable_constraints` (degree/PhD/MBA etc.) live in Stage 3 but are never surfaced in the Prefer UI — so Prefer looks empty even when real preferences exist.
- "Approximate matches only" badge is orphaned from the Prefer UI.
- Home/JdIntake after JD parse does not invoke `resolve-search-intent` / `saveSearchIntent`, so excludes and education constraints never land in current intent.

**Fix (approach a+b):**
- **Minimum required:** Prefer-tab / SearchIntentEditor / display must read Stage 3 `VersionedSearchIntent` including surfacing `unenforceable_constraints` so Prefer doesn't look empty when prefs live in unenforceable.
- **Strongly preferred:** After JD parse, call `resolve-search-intent` / `saveSearchIntent` so canonical intent is Stage 3. Chip editor reads `deal.role_brief_search_intent.current` (conditions + unenforceable), not only `parsedBriefToConditions` Stage 2 mapping.
- **Secondary:** Improve `parse-job-description` degree field / stronger exclude if time — don't treat prompt-only as the full fix.
